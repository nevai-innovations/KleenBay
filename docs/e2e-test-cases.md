# KleenBay end-to-end test cases

Version: 2026-10-02. This is a **test plan, not a test execution report**. It describes the current `apps/web` + `apps/api` application and separately records acceptance tests for requested features that are not built yet. The `prototype/` UI is a reference, not the system under test.

## How to use this document

- **Current** cases target routes/screens in this checkout. Run them in a disposable **local** database first. Repeat the P0 smoke/security set on stage before release.
- **Future** cases are blocked until the named feature exists. Never record them as passed because a prototype, mock, or database model exists.
- P0 = release blocker (security, money, identity, data integrity, core journey); P1 = important workflow/regression; P2 = usability, edge, or noncritical quality.
- Record each result as `PASS`, `FAIL`, `BLOCKED`, or `NOT RUN`; include environment, commit/image digest, tester, timestamp, input fixture IDs, HTTP status, screenshot/trace, and issue link. A test is `PASS` only after observing the expected UI **and** persisted/API state where relevant.
- For negative tests, expected rejection must leave **no unintended row, audit entry claiming success, message, file, payment, or stage change**. Error responses should be structured and must not reveal secrets.
- Use synthetic names, mobiles, and plates. Do not send real messages or reuse customer data. Do not run destructive database tests against the shared stage RDS or any production database.

Current stages are `RECEIVED -> WASHING -> READY -> HANDED_OVER` (UI labels: Received, Started Washing, Ready, Handover). Do **not** test the prototype's six-stage names as if they were current API values. The current UI has Board, Daily Summary, History, Employees, Customers, Vehicles, Services, and Settings for OWNER; Board and History for EMPLOYEE. There is no normal owner-management screen/API in the current one-owner-per-organization model. The owner setup link endpoint is for a provisioned, inactive owner only.

## Environments and fixtures

1. Follow root `README.md`: Node >=22.12, pnpm 11.9.0, Docker Desktop, local PostgreSQL, checked-in migrations, seed, then `pnpm dev`. Web: `http://localhost:5173`; API: `http://127.0.0.1:3000`.
2. Use a **separate local test database** for automated/destructive cases. Seeded local owner credentials are generated by the first seed run; never place them in this document. The local employee code `123456` is a development fixture. The checked-in `kleenbay-stage` ConfigMap selects `OTP_PROVIDER=DUMMY_OTP`, `DUMMY_OTP=123456`; this sends no SMS. Production must select MSG91 and reject fixed codes. The checked-in stage messaging mode is `mock`, meaning `SENT` is simulated delivery, **not** WhatsApp delivery. Verify live configuration separately before stage execution.
3. Prepare organization A with owner A, one branch, active employees A1/A2, inactive employee A3, customers C1/C2, vehicle V1 (ordinary Indian plate), V2 (BH plate), and a service with base, vehicle-type, and branch price. Prepare organization B with owner B, employee B1, customer/vehicle/service/job/invoice/photo with distinct IDs. Create a second branch under A only with **local fixtures** if the test needs it: the current app lists branches but has no branch-creation UI/API.
4. Prepare jobs in every active stage plus one handed-over job, one late job, one ready-waiting job, one paid invoice, one partially paid invoice, and one unpaid invoice. Use distinct idempotency keys unless testing retries. Freeze or control time for expiry, day-boundary, and rate-limit tests.
5. For HTTP authorization tests, use separate cookie jars/sessions for owner A, employee A1, owner B, employee B1, and anonymous. Send the configured `Origin` header on mutations. Record response **keys**, not credentials or OTP values. Avoid printing cookies, passwords, OTPs, provider tokens, or private image bytes in test logs.
